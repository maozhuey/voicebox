## Context

`ProfileList` 当前在每次渲染时将与当前生成引擎兼容的声音档案前置。卡片选择可改变生成引擎，因此同一份档案数据会在一次点击后发生重排。详见 `proposal.md` 的问题背景和 `profile-card-order-stability` 规格。

## Goals / Non-Goals

**Goals:**

- 让卡片展示顺序只由档案查询结果决定，而不由选中状态或当前生成引擎决定。
- 保持已有的兼容性禁用态和不兼容提示，避免改变用户可选择哪些声音的规则。
- 以组件级自动化测试覆盖点击、取消选择和引擎变化三种不重排场景。

**Non-Goals:**

- 不新增手动排序、拖拽排序或持久化排序能力。
- 不改变声音档案创建、删除、导入或接口返回的排序语义。
- 不改变选中卡片后的滚动定位行为。

## Decisions

### 直接渲染查询返回顺序

移除为“支持当前引擎”而建立的排序派生数组，改为直接迭代查询结果。兼容性继续逐卡计算，用于禁用态和说明提示。

备选方案是在首次展示时记录一份本地顺序并在后续渲染复用。未采用该方案，因为接口返回数组已经是唯一数据源；额外状态会增加档案新增、删除、刷新时同步失败的风险。

### 用可观察的卡片顺序验证回归

组件测试将固定模拟档案返回顺序，并在点击动作及引擎变更后读取卡片的可访问名称或稳定标识，逐项比较顺序。该验证直接覆盖用户可见行为，而不是耦合某个内部排序函数。

备选方案是只测试排序辅助函数。未采用，因为当前问题来自组件状态更新路径，纯函数测试无法证明点击后 UI 不会重排。

## Risks / Trade-offs

- [用户可能习惯兼容卡片优先展示] → 继续通过禁用样式和不兼容提示明确表达兼容性，且此变更遵从点击不跳动的产品要求。
- [查询结果的服务端排序变化会反映到 UI] → 这是数据刷新后的正常结果；规格仅保证同一档案集合的交互不会自行重排。

## Migration Plan

1. 更新前端列表渲染逻辑，去除兼容性排序。
2. 补充回归测试并执行前端类型检查、代码检查和测试。
3. 若需回滚，恢复原排序派生逻辑；无数据迁移、API 迁移或部署步骤。
