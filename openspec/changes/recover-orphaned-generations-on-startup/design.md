## Context

现有服务启动流程已对数据库中的活动生成记录做一次清理，串行队列也会对单个执行超时做失败处理。但当前内存队列、工作协程和数据库状态没有统一的运行期健康检查：工作协程停止或任务协程未能写入终态时，后续记录可能仍停留在 `generating`。

## Goals / Non-Goals

**Goals:**

- 使启动恢复与运行期恢复共享相同的“活动记录必须有执行者”语义。
- 保证队列工作协程异常结束后可被监督并恢复，且无执行者的记录在有限时间内结束。
- 保留历史、音频、版本和 CosyVoice 已记录的诊断阶段。

**Non-Goals:**

- 不恢复或重放已中断的 TTS 推理，避免未经用户确认重复生成音频。
- 不改变 CosyVoice 的分段策略、模型加载策略或用户可选的超时配置。
- 不把正常执行中的模型推理误判为孤儿任务。

## Decisions

### 以队列运行态作为活动记录的权威关联

为每个入队和运行任务维护可查询的内存归属，并由一个轻量监督协程检查工作协程是否仍存活。数据库活动记录只有在不属于当前排队集合、运行集合或受监督的交接状态时才会失败。

这样选择是因为数据库只能表达用户可见状态，不能区分“已排队等待”和“执行者已经消失”。仅凭固定时长清理会误伤模型首次加载或较长的 CosyVoice 推理，因此不采用按时间阈值猜测的方案。

### 工作协程异常结束后重启，并进行定向收口

监督协程发现工作协程非预期结束时会创建新的工作协程来消费保留的内存队列；对已从队列取出却不再有运行协程的记录，调用既有历史状态更新逻辑写入失败原因。启动时也调用相同的收口逻辑，避免两套状态含义漂移。

替代方案是服务启动和每个取消请求时全表扫描。该方案不能处理服务运行时工作协程异常，且会让取消接口承担恢复职责，因此不采用。

### 恢复动作只写状态，不移除用户内容

恢复仅更新活动记录到失败并写入稳定的错误文案。音频、版本、文本、收藏状态与故事关联均不改变；这与现有“取消/失败后可重试”的体验一致。

## Risks / Trade-offs

- [内存追踪在进程崩溃后丢失] → 启动恢复把所有上次进程遗留的活动记录定向收口，不尝试重放。
- [监督协程自身失败] → 以受保护的循环和可观测日志启动；关键状态更新失败时记录异常但不终止 API 服务。
- [正常长推理被误清理] → 仅根据本次运行中明确的排队/执行归属判断，绝不以运行时长作为孤儿判断依据。

## Migration Plan

1. 实现队列工作协程监督、状态归属查询与统一的孤儿记录收口。
2. 以服务生命周期和受控队列故障测试验证启动恢复、运行期恢复与正常任务不受影响。
3. 本地构建桌面应用，替换前保留当前应用备份；启动后验证既有活动记录被收口且新任务可进入队列。

若出现误判，可回退至替换前应用备份；已被标记失败的记录保留在历史中，可通过现有重试功能重新发起。
