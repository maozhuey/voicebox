## Context

现有生成队列以一个 `asyncio.Task` 执行每个生成协程。协程无异常返回后，队列只会读取数据库；若记录仍是活动状态，便把它写成泛化的 `Generation interrupted before completion`。因此队列无法分辨运行器忘记发布终态、终态持久化丢失和服务进程已经异常退出。

当前 macOS 运行时会选择 MLX。Qwen TTS 使用一个专属线程运行 MLX，而 Qwen LLM 使用默认线程池；两者没有共享的 MLX/Metal 执行所有权。保留的崩溃报告显示 MLX Metal 命令编码器出现原生 `SIGSEGV`。原生进程终止不能由 Python 的异常处理捕获；服务下次启动时，现有恢复逻辑又把这类记录和协程无终态返回混为一谈。

本设计实现 `proposal.md` 和 `specs/generation-terminal-status/spec.md` 中的行为，不修改用户输入、声音选择或引擎选择规则。

## Goals / Non-Goals

**Goals:**

- 让后台队列仅在已知终态、明确取消、超时或服务关闭后释放任务所有权。
- 以单一 MLX 执行通道串行化 TTS、LLM 与 MLX STT 的模型加载、推理和释放，消除跨线程/跨模型同时提交 Metal 命令的竞态。
- 用明确的、脱敏的诊断区分终态未发布、工作协程异常、超时、取消、正常服务关闭和异常服务退出。
- 让异常服务退出后的下一次启动安全收敛遗留任务，并让后续队列任务继续运行。

**Non-Goals:**

- 不自动重放中断任务，避免重复写入音频或故事时间线。
- 不把 Qwen 默认降级为 CPU，也不更改用户选择的 TTS 引擎。
- 不捕获或展示原生崩溃堆栈；原生崩溃只能通过预防并发、生命周期记录和下一次启动恢复来处理。
- 不回填旧历史记录，因为旧记录没有足够的可靠因果信息。

## Decisions

### 1. 使用显式运行结果，而不是以协程“没有抛异常”作为成功信号

`run_generation` 将返回一个小型、仅进程内使用的运行结果，声明它已发布的终态和退出类别。发布终态后，队列用独立数据库会话核验记录确实为终态；只有“运行结果”和持久化状态一致时，任务才释放所有权并开始下一个任务。

若运行器返回但没有成功发布终态，队列使用新的独立会话写入“终态未发布”失败，且将当前分段进度保留。若运行器抛出异常但未自行发布终态，队列写入“工作协程异常退出”。已有的取消、超时和完成结果保持原样。

选择此方案是因为数据库是桌面 UI、SSE 和启动恢复的共同事实来源；只依赖 Python task 的完成状态无法证明用户可见状态已经提交。仅调整现有泛化字符串不能修复所有权过早释放，故不采用。

### 2. 终态诊断使用受限字段和本地 JSONL 记录

新增生成诊断写入器，向数据目录的日志子目录追加一行 JSON。每条记录生成随机诊断编号，字段仅包括生成 ID、引擎、型号、最近进度、退出类别、服务生命周期类别和时间。历史表 `error` 保存稳定错误代码与诊断编号，客户端按错误代码映射文案。

诊断不保存用户正文、参考音频路径、绝对路径、原始异常消息或堆栈。这样可关联一次失败，又不会把私人朗读内容写入额外日志。选择 JSONL 而不是新增数据库表，避免为诊断保留引入迁移与主业务查询耦合；诊断文件可在本地支持排查时按编号读取。

### 3. 用原子生命周期标记识别非正常服务退出

服务启动时原子写入带实例 ID 的 `running` 生命周期标记；正常 lifespan 关闭完成队列收敛后，原子改写为 `clean_shutdown`。下一次启动如果看到上个实例仍是 `running`，在孤儿任务恢复前把该次恢复归因为异常服务退出，并为每条任务写入相应诊断。正常关闭导致的任务取消保留单独原因。

这一标记可覆盖 MLX/Metal `SIGSEGV` 等无法执行 Python finally 的情况。选择标记文件而不是仅依赖进程 PID 或崩溃报告：PID 可能被复用，崩溃报告可能延迟或被系统清理，而原子标记在每个支持的平台都可用。

### 4. 所有 MLX 原生工作共享一个持久执行通道

新增进程级 MLX 运行时协调器：它持有一个单线程执行器和异步排队接口。MLX TTS、MLX LLM 与 MLX STT 的加载、生成、缓存清理和卸载都通过该通道执行；非 MLX 的 PyTorch 和 CosyVoice 路径不改变。执行通道的所有权跨完整的原生调用保持，不能在模型加载后切到另一个线程。

这直接消除当前 TTS 专属线程与 LLM 默认线程池并存时对同一 Metal 运行时的并发访问。选择全局单通道而不是为每个模型增加锁：每模型锁仍会允许 TTS 与 LLM 同时提交 MLX Metal 命令；每次调用新建线程又会重新引入线程绑定问题。吞吐会串行化，但桌面端本就只允许一项 TTS 生成，捕获精修相对于进程崩溃的代价可接受。

### 5. 客户端只展示可行动的安全错误

错误映射识别稳定代码，生成“在第 x/y 段中断，可重试（诊断编号：…）”或“本地服务异常退出，可重试（诊断编号：…）”。原始后端错误仍只写入开发日志，不向 UI 或 API 透出。未知错误继续使用现有通用映射。

## Risks / Trade-offs

- [MLX 全局串行化会延后捕获精修] → 以 FIFO 等待换取 Metal 原生稳定性；UI 已有异步状态，不阻塞界面。
- [原生 MLX 缺陷在串行化后仍可能崩溃] → 生命周期标记让本次任务得到精确、可重试的失败；将崩溃发生时的并发信息写入诊断，作为进一步升级 MLX 或引入独立推理进程的依据。
- [终态恢复写入遇到 SQLite 锁] → 使用短生命周期的新会话、有限重试和错误日志；仅在成功持久化或明确报告持久化故障后才释放队列所有权。
- [应用被强制杀死没有正常关闭标记] → 视为异常退出是保守且安全的；不会重放或删除音频。
- [生命周期标记损坏] → 将其作为未知上次退出处理并记录诊断，不能阻止服务启动。

## Migration Plan

1. 实现运行结果、诊断写入和终态核验，并先通过后端单元测试。
2. 接入生命周期标记和 MLX 全局运行时协调器，覆盖并发与异常退出恢复测试。
3. 接入客户端错误映射并完成客户端测试、类型检查和构建。
4. 在本地开发服务与本地 Docker 环境进行健康检查；macOS 桌面端使用三段 Qwen 合成和一次捕获精修验证串行化与终态展示。
5. 若需回退，移除新版桌面包并恢复上一应用副本；新产生的诊断 JSONL 不影响既有数据库和音频文件。
