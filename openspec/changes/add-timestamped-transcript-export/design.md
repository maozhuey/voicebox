## Context

参见 [proposal.md](proposal.md)。当前 STT 抽象、MLX 后端和 PyTorch 后端都只向调用方返回字符串；`/transcribe` 只返回全文与总时长。捕获表只持久化 `transcript_raw` 和可选的 `transcript_refined`，捕获详情页则在客户端直接生成现有 TXT、Markdown 和 WAV 导出。

Whisper 在推理阶段能够产生分段边界，但当前 PyTorch 路径只利用 timestamp token 完成长音频滑窗，随后将其丢弃；MLX 路径也只从结果中读取 `text`。时间戳必须在后端第一次获得模型结果时保留下来，不能在客户端根据字符数或总时长补算。

## Goals / Non-Goals

**Goals:**

- 用一个后端领域结果同时承载 Whisper 原始全文和原始分段，覆盖所有转录入口。
- 对外同时提供便于展示/导出的格式化文稿与便于程序消费的结构化分段。
- 用兼容迁移保存捕获分段，保证重新转录替换数据时的原子性。
- 让桌面端导出逻辑可单独验证，且始终导出原始分段。

**Non-Goals:**

- 不给精修文本重新对齐或生成推测时间戳。
- 不回填升级前旧捕获的时间轴；用户需要时可重新转录。
- 本次不新增 SRT、VTT、逐词时间戳编辑器或时间轴可视化。
- 不改变 Whisper 模型选择、Qwen 精修规则及现有导出格式。

## Decisions

### 1. STT 后端统一返回结构化转录结果

在 STT 抽象层定义一个结构化结果，其中 `text` 保存 Whisper 原始全文，`segments` 保存规范化后的 `start_ms`、`end_ms` 和 `text`。MLX 后端从模型结果的分段集合读取边界；PyTorch 后端启用 Whisper 分段时间戳输出，并从模型的 timestamp token/分段输出解析边界。所有调用点只消费同一结构，避免捕获服务和 `/transcribe` 各自解析不同模型的私有返回值。

规范化阶段负责：删除空文本分段；拒绝非有限、负数或结束早于开始的边界；转换为整数毫秒；保持开始时间升序；将 Whisper 短音频 30 秒填充窗口产生的末端越界裁剪到真实音频总时长，并丢弃完全落在音频总时长之后的填充分段。若最终没有有效分段，本次请求失败，不用一个覆盖全片的虚拟分段冒充精确时间戳。

备选方案是继续返回字符串并增加第二次识别专门获取时间戳。该方案会使一次捕获执行两次大模型推理，增加等待时间和结果不一致，因此不采用。

### 2. API 同时返回结构化分段和派生文本

`/transcribe` 保留 `text`、`duration`，新增 `segments` 与 `timestamped_text`。捕获响应保留 `transcript_raw`，新增可选 `transcript_segments` 与 `transcript_timestamped`。字段采用新增方式，不重命名旧字段，从而兼容农小册等现有调用方。

`timestamped_text` 不单独保存，由同一个纯格式化函数从结构化分段派生，格式固定为 `[HH:MM:SS.mmm --> HH:MM:SS.mmm] 原始文本`。这样可避免 JSON 分段与另一份持久化字符串发生漂移，同时仍向用户和调用方提供“额外一份带时间戳原始文本”。

公开契约以 FastAPI 的运行时 OpenAPI schema 为唯一来源。静态 OpenAPI 副本和桌面端生成客户端必须由该 schema 更新；README 与开发者指南的示例必须使用实际请求字段 `file` 以及 API 枚举值 `turbo`。模型管理内部使用的 `whisper-turbo` 标识仅用于下载和状态管理，不能作为 `/transcribe` 的 `model` 参数。`large` 与 `turbo` 均使用同一响应结构，既有 `text`、`duration` 字段保留不变。

备选方案是只返回格式化字符串。该格式便于阅读，却迫使剪辑调用方重新解析文本才能做时间轴计算，因此同时提供结构化字段。

### 3. 捕获表使用可空 JSON 文本列保存分段

在 `captures` 表增加可空的 `transcript_segments` 文本列，内容为结构化分段 JSON。桌面应用采用单用户 SQLite，现有迁移机制通过列存在性检查执行幂等 `ALTER TABLE`；旧行保持 `NULL`。读取时对损坏 JSON 做防御性处理并视为无时间戳，不能影响捕获列表加载。

创建捕获时在一次数据库提交内保存全文和分段。重新转录先在内存中获得并验证完整结果，再在一次提交内替换全文与分段并清除过期精修；失败时不修改旧行。

备选方案是建立一张逐分段子表。当前分段只随捕获整体创建、读取和替换，没有独立查询或编辑需求，JSON 列更符合现有 `refinement_flags` 的轻量存储模式。

### 4. 客户端使用原始分段生成导出文件

捕获详情页新增菜单项和独立导出处理函数。时间格式化与文稿构建放在无 UI 依赖的纯函数中，以便覆盖小时进位、毫秒补零、顺序和空段等测试。文件名使用 `capture_<短ID>_timestamped.txt`，保存编码沿用 Tauri `writeTextFile` 的 UTF-8 文本写入。

导出只读取 `transcript_segments`，不读取当前“精修/原始”页签状态。没有分段时菜单项仍可被用户触发以显示“重新转录后可用”的明确提示，但不会打开保存对话框。

备选方案是新增后端下载接口。现有 TXT 和 Markdown 都由客户端生成，新格式数据量很小，继续使用同一保存流程可以减少接口和临时文件管理。

## Risks / Trade-offs

- 不同 Whisper 实现的分段输出形状可能不同 → 在各后端适配私有结构，在统一边界做严格规范化，并用模型返回桩分别测试 MLX 与 PyTorch。
- 长音频可能产生较大的 JSON 字段和列表响应 → 分段粒度沿用 Whisper 的自然分段，不生成逐词记录；相对音频文件体积可忽略。
- 浮点秒转换为毫秒存在舍入误差，Whisper 也可能把短音频末段延长至 30 秒填充窗口 → 统一四舍五入为整数毫秒，并把分段限制在真实音频时长内。
- 旧捕获没有时间戳 → 保持字段为空并提供重新转录路径，不生成不可验证的数据。
- 静态或生成型 API 工件可能滞后于运行时 schema → 将工件同步纳入回归验证；若调用方严格拒绝未知字段，需同步升级其响应类型，而非删除新增字段。
- 当前 Voicebox 工作区存在其他未提交改动 → 实现只修改本变更涉及的行，提交前按文件和 diff 逐项核对，避免覆盖现有工作。

## Migration Plan

1. 先增加向后兼容的数据模型、捕获列迁移和读取逻辑；旧数据库升级后原有行保持可读。
2. 更新 STT 后端和 API，使所有新转录先产生并验证分段，再持久化。
3. 更新客户端类型和导出菜单，最后运行迁移、后端测试、前端类型检查及本地桌面端手工验收。
4. 回滚时客户端可忽略新增字段，旧版本也会忽略 SQLite 中的附加列；无需删除用户数据。
