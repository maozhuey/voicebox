## Context

当前 `POST /captures` 与 `POST /captures/{id}/refine` 是两个独立请求：前者已提交音频、原始转录和捕获记录后，客户端才根据 `auto_refine` 发起后者。精修服务直接调用 `backend.generate()`，而该调用将模型加载和实际解码合并；路由又把所有异常的原始文本直接作为 500 响应。因此，已成功的听写会在界面上被后续精修的通用 HTTP 错误覆盖，且无法从本地记录判定故障位置。

项目已有 `capture-diagnostics.jsonl` 的安全诊断写入器：它会持久化固定字段，脱敏异常文本，并在写入失败时不影响主请求。本设计复用这一持久化方式，不新增数据库表或云端遥测。动机和用户可见契约见 `proposal.md` 与 `specs/capture-refinement-recovery/spec.md`。

## Goals / Non-Goals

**Goals:**

- 将精修执行拆成可归因的模型加载、LLM 生成和数据库保存边界。
- 让自动精修失败仍以原始转录完成当前听写会话的交付；手动精修失败不改动现有捕获。
- 在不保存原始转录、音频路径、异常原文或堆栈的前提下，使支持人员能通过诊断编号和阶段排查问题。
- 为后端阶段归类、数据保留和前端自动回退建立可重复的回归测试。

**Non-Goals:**

- 不修改 Whisper 转录、模型下载、Qwen 推理算法、模型选择逻辑或精修提示词。
- 不为模型加载或生成新增重试、超时或后台队列；这些会改变延迟和资源策略，应单独设计。
- 不将诊断上报到网络、不存储可识别的音频或转录内容，也不更改已有成功捕获的结构。

## Decisions

### 1. 在精修服务中显式预加载 LLM，再调用生成

精修服务在构造提示词后先调用所选后端的 `load_model(resolved_size)`，并将此调用失败包装为内部 `CaptureRefinementError(stage="model_load")`；加载成功后再调用 `generate()`，将其后的异常包装为 `stage="llm_generate"`。现有 Qwen 后端的 `generate()` 保留自身的加载保障；因为模型已加载且尺寸一致，该调用是无副作用的快速返回。

这样可以在不改动不同 Qwen 后端公共生成契约的情况下，准确区分首次加载失败和已经可用模型的实际生成失败。备选方案是让两个 Qwen 后端的 `generate()` 返回阶段枚举；这会把捕获专属诊断侵入所有 LLM 使用者，且需要同步改动 PyTorch 与 MLX 两条实现，收益不足。仅按异常字符串猜测阶段也被排除，因为库版本变化会使归类不可靠。

### 2. 使用捕获专属异常和安全诊断响应

`CaptureRefinementError` 只携带固定阶段和原始异常作为 `__cause__`，不把原始异常文本返回给客户端。精修路由捕获该异常，并调用新的精修诊断记录入口写入 `kind: "refinement"`、阶段、捕获来源、LLM 尺寸、异常类型和固定脱敏摘要，随后返回 `CAPTURE_REFINEMENT_DIAGNOSTIC:<id>`。数据库保存异常在服务中执行 `db.rollback()` 后也包装为 `stage="persist"`。

诊断记录保持与现有 JSONL 相同的 1 MB 轮转和“诊断写入失败不影响主流程”规则。它不写入 capture ID、文件名、音频路径、原始或精修文本；这些字段不是定位阶段所必需且会扩大本地敏感数据面。备选方案是把原始 `str(error)` 直接透传，或为精修另建数据库表；前者会泄露内容与路径，后者增加迁移和数据保留负担，均不符合该故障的本地、最小化诊断需求。

### 3. 将精修写回保持为单一提交，并在失败时回滚

仅当 LLM 成功返回非空精修结果后，服务才设置 `transcript_refined`、`llm_model` 和 `refinement_flags`，随后一次 `commit`。任何保存/刷新失败都会回滚当前 SQLAlchemy 会话并返回 `persist` 诊断；因此音频、原始转录和已有精修版本不被覆盖。

备选方案是预先写入“精修中”状态或在失败时清空精修文本。这会使正常捕获多出状态迁移，并可能损坏用户此前可用的精修结果，故不采用。

### 4. 自动与手动精修按发起上下文采用不同的恢复行为

客户端把精修 mutation 的输入从裸 `captureId` 扩展为带 `mode` 与自动精修时的原始捕获快照的请求上下文。自动精修失败时，失效并广播该已创建的捕获、调用既有 `onFinalText(transcript_raw, capture, allowAutoPaste)`，并显示“转录成功，精修失败，已保留原始转录”的安全提示和诊断编号。手动精修失败只显示“精修失败，原有内容未改变”的提示，不再次触发复制或自动粘贴。

这样保留了自动听写对外的“文本一定交付一次”行为，同时避免用户点一次手动精修就重复粘贴文本。备选方案是把所有失败都只显示 toast；它无法修复浮动听写窗口在精修失败时丢失交付的问题。把原始文本塞进后端 500 响应也被排除，因为客户端已经拥有刚创建的捕获快照，且错误响应不应承载用户文本。

## Risks / Trade-offs

- [显式预加载会令首轮精修仍需等待模型加载] → 这是原有 `generate()` 已有的成本；本设计只将其归类，不额外加载模型。
- [数据库提交发生不确定性错误时，客户端无法获知是否已落盘] → 服务先回滚且客户端刷新捕获列表；本地 SQLite 的单进程提交失败通常可恢复，诊断记录可用于进一步核实。
- [自动精修失败后的原始文本交付与成功精修一样触发自动粘贴] → 只对自动发起的精修执行一次，并复用捕获创建时快照的 `allow_auto_paste`。
- [诊断 JSONL 写入本身失败] → 按现有策略吞掉该 I/O 异常，仍返回精修失败；诊断编号只是不可查询而不会改变用户数据的安全性。

## Migration Plan

1. 先加入服务异常、阶段化诊断和事务回滚，并以单元/API 测试验证原始捕获不变。
2. 再接入客户端错误映射与自动回退，运行前端与后端回归测试。
3. 在本地开发服务器和本地 Docker 环境验证一次成功转录后人为触发精修失败的交付行为；随后构建并替换本机桌面包，以确认已安装应用使用新侧车与前端。
4. 若需回滚，恢复上一桌面包/后端构建即可；诊断 JSONL 为附加日志，不需要数据迁移或清理。
