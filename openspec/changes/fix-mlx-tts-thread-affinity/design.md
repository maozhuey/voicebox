## Context

`MLXTTSBackend` 目前使用 `asyncio.to_thread` 分别执行阻塞的模型加载和生成。默认线程池不保证同一任务在同一条线程运行，而 MLX 的 GPU stream 为线程本地资源。已安装桌面应用在“先加载、再生成”时复现了 stream 缺失异常。动机见 `proposal.md`，行为契约见 `specs/mlx-tts-thread-affinity/spec.md`。

## Goals / Non-Goals

**Goals:**

- 让每个 MLX TTS 后端实例的加载、推理都在固定的单线程执行器中完成。
- 继续通过 `await` 让 HTTP 事件循环保持可响应，并保留现有生成队列对 GPU 任务的串行化。
- 使用无真实模型权重的单元测试验证调度约束。

**Non-Goals:**

- 不修改 Qwen 模型、缓存位置、请求/响应 API 或语音档案。
- 不改变 MLX STT、Qwen LLM 或其他 TTS 引擎的线程模型。
- 不尝试将 MLX 任务并行化；单条线程是该运行时的正确性约束。

## Decisions

### 每个 MLX TTS 后端维护专用单线程执行器

后端在初始化时创建一个 `max_workers=1` 的执行器，并通过一个异步帮助方法将加载和推理提交给它。这样模型、默认 GPU stream 和推理始终属于同一 OS 线程。

备选方案是继续使用 `asyncio.to_thread` 并以锁包裹调用；锁只能阻止并发，不能保证线程一致，因此不能解决 stream 线程本地问题。另一方案是在事件循环线程直接运行推理；这会阻塞 API、SSE 和取消处理，不可接受。

### 最小化修复范围并以模拟调用测试执行器选择

测试将替换后端的同步加载/生成实现和执行器提交入口，验证两个操作都被路由到同一专用执行器，而不下载模型或调用 GPU。该测试覆盖错误根因，而不是依赖硬件和大模型权重的端到端环境。

## Risks / Trade-offs

- [单线程串行化限制同一后端吞吐] → 现有生成队列已将 GPU TTS 串行化，修复不会降低现有并发模型。
- [执行器在线程生命周期内常驻] → 每个后端进程仅有一个实例；进程退出时由运行时回收，且不增加额外模型副本。
- [已有运行中的旧侧车不含修复] → 重新构建、签名并替换桌面侧车后重启应用；保留现有应用备份以便回退。

## Migration Plan

1. 添加专用执行器与回归测试，并执行目标后端测试。
2. 构建新的冻结侧车，在隔离数据目录完成 Qwen 生成验证。
3. 重新打包、签名并替换本地 macOS 应用，保留当前应用备份。
4. 启动桌面端并以健康接口及 Qwen 实际生成验证；失败时切回备份应用。
